# 两会话修 bug

调用本 skill 的会话是 **A**：诊断、写交接材料、监督、裁决、验收，并且是唯一和用户对话的会话。**B** 是 A 开的后台子 agent，只读 [b.md](b.md)，在任务 worktree 里按冻结的方案先红后绿。

按需读：建 flow 文件时读 [files.md](files.md)；第 5 步开 B 之后立刻读 [supervise.md](supervise.md)，里面是监视脚本的事件、监督、终审和交付；审查时读 [review.md](review.md)。

调用本 skill，就是要求 A 在 Cursor 里用 Shell 的 `notify_on_output` 监视 B，并授权 A 在 P0 和判卡住时对 B 设 `interrupt`，也授权 A push 任务分支、建 Draft MR/PR，快修和豁免档里还授权 A 自己 commit。合入不在这份授权里，见「交付报告」。

简单问题不开 B：快修档，以及第 4 步判为豁免的问题，A 单会话修完。

## 依赖

- `fixing-bugs`（<https://github.com/Shengjingwa/fixing-bugs>）：先找本 skill 目录的同级目录 `../fixing-bugs/`，找不到再按宿主的 skill 清单找。A 用它的「开头」「升档」「快修」「排查」「停下与交付」和 `full.md` 第 1–4 段，豁免且有风险信号时读到第 6 段；B 用 `full.md` 第 5–6 段，和 `b.md` 不一致的地方以 `b.md` 为准。本 skill 要 commit、push、建 Draft MR/PR，和「停下与交付」里「改动默认留在工作区」相反，以本 skill 为准。读不到时按 `fixing-bugs` 的「依赖」一节处理：标 `blocked`，写明缺什么，继续不依赖它的部分。
- `diagnosing-bugs`、`tdd`：`fixing-bugs` 已声明，读取方式同上。

## 1. 开头

1. 查有没有人已经在修：读这个问题的 issue 评论和关联的 MR/PR，再按模块路径或关键词搜同一仓库里还开着的 MR/PR；模块还不清楚的，第 3 步定位到模块后再搜一次。GitLab 上调 `GET /projects/:id/issues/:iid/related_merge_requests?per_page=100`，响应头 `X-Next-Page` 不为空就接着翻页。它列出提到这个 issue 的 MR 和 issue 自己引用的 MR，包括别的项目的，每张带 `state`。`state` 为 `opened` 的逐张看标题和描述，确认是在修这个问题；只是顺带提到它的不算。issue 的 `merge_requests_count` 只数会关闭它的 MR，`closed_by` 接口常连这些也返回空，都不能拿来判断。有别人在途的修复时，停下告诉用户，不建现场。
2. 主仓库在本地时，再查本机还没推送的在途改动：flow 仓库 `registry.md` 的「待收尾」、项目的在途清单（有的话），以及 `git -C <主仓库> worktree list` 列出的每个别的 worktree，看 `git --no-optional-locks -C <它> status --short` 和 `git --no-optional-locks -C <它> diff --stat <目标分支的上游，例如 origin/main>...HEAD`（那可能是别的 B 正在用的现场，不加这个选项会抢它的 `index.lock`）。在修同一个问题的，按上一条的在途修复处理；只是改到同几个文件的，在对话里列出来，交付前同步目标分支时再看一次。
3. 做 `fixing-bugs` 的「开头」：记主仓库基线，写一句现象和修好标准，定起始档位。主仓库不在本地（或只有临时目录里的浅克隆）时，先完整克隆到 `<父目录>/<repo>`（`<父目录>` 用用户放其他仓库的目录），基线记「新克隆，无改动」。
4. 给这个 bug 起一个短名 `<短名>`（小写短横线，例如 `csv-missing-row`）。
5. 起始档位是快修：照样做第 2 步建现场，在任务 worktree 里按 `fixing-bugs` 的「快修」修完，收尾和交付同第 4 步的豁免。要问用户的（缺提交身份、目标分支待用户），commit 前一次问齐。快修中碰到升档信号时：把修之前失败的那条命令或测试复制进 flow 的 `repro/`，撤回 worktree 里快修的全部改动，按第 2 步第 7 条补齐硬条件核对，再做第 3 步。

一次请求里混着仓库外的记录活（往 issue、wiki 里记事实）时，这部分不进 duo：A 直接做，交付报告里单列。改仓库里的文档照快修走。写给别的团队的契约或文档，验收不看步数，看每条事实是否都有 A 亲自核对过的出处（代码路径加行号，或数据、日志）；核对不了的，在文档或 MR/PR 描述里标出来，也写进交付报告。

一次请求里有好几个问题时，先分拣再开工：在 flow 仓库根目录写 `triage-<日期>.md`（flow 仓库还没有就先按第 2 步第 6 条建），一个问题一行：问题和出处、归属（本仓库，或别的团队、别的仓库）、涉及的模块或文件（还不清楚写「待诊断」）、有没有人在修（按上面第 1、2 条查）、要不要用户定口径、去向（开任务的写短名，其余写交给谁或在等什么）。commit 后逐个开任务，交付报告引用这张表。项目的合入是串行的（每合一张，其余都要重新变基、重审）时，同一仓库里模块相邻、各自都小的几个问题可以并成一个任务：一个短名、一个 worktree、一张 MR/PR，每个问题单独 commit，MR/PR 描述逐条对应到问题。

分拣出的几个任务可以同时推进，并行来自几个 B 同时在跑：A 一次只诊断一个任务，手上的任务在等 B 或等用户时，再去做下一个。同时在跑的 B 最多 2 个，从开 B 算到这个任务发出交付报告或提前结束（第 9 步）；快修和豁免不开 B，不占名额，交付后为评审意见 resume B 也不占。名额满时，A 可以先诊断下一个任务，等占着名额的任务交付或结束，再开它的 B。两个任务要改同一个函数或同一段配置时（第 3 步定位到的代码位置重叠；快修在动手前按日志指向的位置比），后一个排队：清掉打点，把根因和代码位置写进 flow 的 `<短名>/` 并 commit，在本任务「待收尾」那一行的备注写排在哪个短名后面。前一个合入或放弃后，删掉这条备注；起点是上游的，`git -C <worktree> fetch <远端>`，再 `git -C <worktree> merge --ff-only <远端>/<目标分支>`（诊断不 commit，能快进），起点 sha 改记新的上游；起点是 `HEAD` 或快进报错时，停下问用户。然后重跑原始复现：问题还在，先在新代码上核对根因和代码位置，再接着往下做；复现不出多半是前一个任务顺带修好了，告诉用户，确认后按第 9 步结束。只是改到同一个文件的不同地方的，照上面第 2 条列出来，可以同时跑。

结果不确定的 bug（同一输入要跑多遍看通过率，例如模型效果）：修好标准写成通过率，目标用例达到用户给的门槛，其余用例不低于修前基线。遍数在第 3 步定，修前基线按同样遍数跑出来，记进 `test-plan.md`；没有 `test-plan.md` 的快修和豁免，记在对话里。第 4 步的一轮耗时按跑一遍算。

修法的对错只能靠评测读数判时（例如改提示词）：
1. 门槛、数据集和遍数在第一次读数之前写进 flow 的 `<短名>/` 并 commit，之后的 `test-plan.md` 引用它。同时把修好标准和上线后要核的每条行为列成表，每条写哪个门槛项量它；量不了的，写明上线后怎么核、没做到算什么（回滚，还是另开单）。两样都没有的行为，不写进验收结论。
2. 比较几种候选写法属于诊断，由 A 只在和验收集不重叠的开发集上比。有候选在开发集上过了门槛，才冻结方案。换了 3 种实质不同的写法都没过门槛，停下报给用户。没过门槛时，先分清失败样本是模型行为没达标，还是重放 harness、判分器或接口出了错（例如漏拼上下文、判分规则写错、超时返回空串）。后者都不算用掉一种写法：接口异常只补跑出错的样本；harness 或判分器的修改和原因先写进 `<短名>/` 并 commit，之前的读数（各候选的和修前基线）都作废，重跑再比。判分器改后判得更宽的，算放宽验收门槛，先问用户。
3. 验收时用分支代码在验收集上再量一次。实现只是把量门槛时重放用的输入（例如提示词、消息文本）搬进代码时，验收集上的读数可以继续用重放跑出来，再核对代码在验收集每个样本上生成的输入和重放用的逐字节相同。
4. 数据集只覆盖它收进来的输入。交付前的审查加一项：列出改动会走到的每类输入或调用路径（例如没调用某个工具的回合），各写出在数据集里有几个样本；样本为 0 的，在代码里排除，或者补测试再交付。本来不派审查 agent 的快修和豁免，这类修法也按 [review.md](review.md) 的固定前缀派 1 个，专查这一项；开了 B 的档位交给维度 1 的 agent。

有上线后才做的核对时（例如在测试环境问几道题），每条写明它会走到哪段被改的代码，以及依据（例如离线重放里这道题触发过几次）。线上触发不了的路径照实写明，换成上线后查一段时间日志里这条路径的次数和样本。有 `test-plan.md` 的写进用例行，没有的写进 MR/PR 描述。

用来做新功能时，流程照走，几个说法这样换：现象写成现在缺的行为；修好标准写成验收命令通过、看到新行为；原始复现写成现在会失败的验收命令，`handover.md` 的「预期失败样子」写新能力缺失时的现行为；根因写成要改的代码位置。`full.md` 第 2 段的假设排序、探测证据和排除证据都写「N/A：新功能」，第 3 步的完成条件换成：验收命令在 worktree 上跑过、失败的样子写在对话里，要改的代码位置带路径和行号，命令已放进 flow 的 `repro/` 并 commit。S0 的基线失败常常是「无」，这是正常的。工作分支用项目的功能分支前缀，例如 `feat/`。

一个任务要改几个仓库时，每个仓库单独建现场、单独分流，步数少的仓库（例如只改配置）常落进豁免。仓库之间的合入和上线顺序写进交付报告。

**完成：** 对话里有在途修复的查询结果、基线摘要、一句话现象和修好标准、起始档位、`<短名>`。

## 现场

| 位置 | 路径 | 写者 |
|---|---|---|
| 主仓库 | `<父目录>/<repo>` | 全程不写，只用来记基线和建 worktree |
| 任务 worktree | `<父目录>/<repo>-wt-<短名>`，工作分支 `fix/<短名>`；项目对 worktree 路径或分支名有规范时按规范 | 分时独占，见下 |
| duo 目录 | worktree 私有 git 目录下的 `duo/`：`git -C <worktree> rev-parse --absolute-git-dir` 的输出加 `/duo`。放 `progress.md`、`logs/` 和 `running` 标记 | A 建目录，之后只有 B 写 |
| flow 仓库 | `<父目录>/<repo>-flow/`，自带 git；本任务子目录 `<短名>/`，根目录有 `registry.md` | 只有 A |

duo 目录不在工作区里，`git status` 看不到它，也不用改 `info/exclude`；`git worktree remove` 时它会一起删掉。

**运行生成物**：跑复现或测试时自动生成、项目又没有忽略的缓存和编译产物，例如 `__pycache__/`、`bin/`、`obj/`。worktree 是从一个 commit 新建的，所以里面的未跟踪文件只可能是 A 或 B 造出来的。运行生成物不算打点，不提交，也不让 worktree 变脏。下文说 `git status --short` 为空，都是指除了运行生成物以外为空。

任务 worktree **分时独占**：
- A 诊断期间由 A 独占。A 的打点从不 commit，交给 B 前清理到 `git status --short` 为空。
- B 在跑时由 B 独占，A 只读。A 读 git 一律加 `--no-optional-locks`，审查钉在 commit sha 上，不读 B 的工作区。
- B 结束本轮、A 还没 resume 它时，A 可以在 worktree 里运行命令。B 结束本轮以宿主的通知为准，退路里以 `STATUS:` 行末的 `@<时:分:秒>` 为准。在 Cursor 里，宿主的通知要等 A 这一轮结束才送到；A 等不到时（例如在 `/goal` 下一直不结束本轮），看 `handover.md` 里记的 B 的转录，最后一行是 `"type":"turn_ended"` 才算，没传转录就结束这一轮，等通知。子 agent 的 B 先写 `progress.md` 的 `STATUS:` 行，写完还在回复，不能单凭它判断。A 不改跟踪文件，不 commit，不 checkout，跑完后 `git status --short` 和 B 交回时一致。例外都在 B 交回 `DOD` 之后：「交付前同步」第 4 条；按「快修和豁免的 MR/PR 评审意见」第 2 条把 worktree 跟到 MR/PR 现在的 head；supervise.md「跟到合入」里修变基弄坏的合并类文件。A 的 shell 跑完就切回 flow 仓库：Windows 上，shell 的工作目录停在 worktree 里，第 9 步就删不掉它。
- B 在跑而 A 要亲手做实验时，A 用 `git worktree add --detach <临时路径> <sha>` 开临时 worktree，用完即删。

A 和 B 都不用 `git stash`：stash 栈由同一仓库的全部 worktree 共享。

flow 仓库里的每次写入，A 都立即 commit。**先落盘再回复**：裁决、审查结论和攒批意见，都要先写进文件、commit 之后，才算做完，才能通知 B 或回复用户。

**门槛硬条件**，碰到任一条就不能豁免（第 4 步的登记类豁免除外）：
- 需要外部裁决：改动会改变别的团队、协议或接口属主定下的约定。
- 碰到关键路径：按 `registry.md` 的关键路径清单判断，看行为不看文件。只改清单里文件的注释、文档或说明字段，代码和门禁读它的方式和结果都不变时，不算碰到。
- 属于历史翻车域：`registry.md` 里该模块出过 P0 或 P1，或者该模块的 git 历史里有回滚、热修提交。

A 先自己判断，拿不准才问用户：
- 关键路径清单为空时，A 按代码先拟一份，写进 `registry.md` 并标「A 推断」。参考范围：鉴权与权限、资金与计费、数据写入与迁移、对外接口与协议、密钥与安全、并发与调度核心。
- 历史翻车域：查 `registry.md`，再运行 `git -C <主仓库> log --oneline -i -E --grep "revert|hotfix|回滚|热修" -- <模块路径>`。两处都没有记录，就算未命中。
- 外部裁决和关键路径：从代码和方案能确认没碰到，就算未命中；碰到了，或者拿不准，问用户，时机见第 4 步。
- 用户答不上，按命中处理，在 `registry.md` 记「用户不确定」，下次同一模块直接按命中，不再问。用户的答复都写回 `registry.md`。

## 2. 建现场

1. 记下目标分支：`git -C <主仓库> branch --show-current`。输出为空（detached HEAD）时，目标分支记为「待用户」。
2. 定起点：运行 `git -C <主仓库> rev-parse --abbrev-ref '<目标分支>@{u}'`（PowerShell 里不加引号，`@{u}` 会被当成脚本块，git 根本不运行）。打出上游名（例如 `origin/main`）时，先 fetch 它的远端（例如 `git -C <主仓库> fetch origin`），fetch 之后再取上游的 sha，不沿用前面查资料时记下的，起点用这个上游分支，fetch 失败也照样用它，在对话里说明它可能落后。报 `no upstream configured`，或目标分支是「待用户」时，起点用 `HEAD`，并在对话里说明。记下起点的 sha，后面凡是用到起点都用这个 sha。从上游建，MR/PR 就不会带进主仓库没推送的 commit，也不用为了同步去 pull 或清理主仓库。
   上游的远端（例如 `origin`）就是之后 push 用的 `<远端>`；起点是 `HEAD` 时看 `git -C <主仓库> remote`，不止一个就问用户。
3. 建任务 worktree：`git -C <主仓库> worktree add -b <工作分支> <worktree 路径> <起点 sha>`。用 sha 建，工作分支不会把上游设成目标分支。运行前先查短名用过没有：工作分支，以及 flow 仓库里的 `<短名>/`、`archive/<短名>/` 和 tag `<短名>-v1`。任一项已经存在，短名依次加后缀 `-2`、`-3`，直到四项都不存在。
4. 建 duo 目录和其中的 `logs/`。项目需要装依赖时，在后台装，输出写进 `logs/deps.txt`，命令结束时追加一行 `DEPS_DONE exit=<退出码>`，不等它结束，直接往下做。构建或跑测试要从主仓库补不入仓的文件（被 gitignore 的二进制、源码目录、签名材料等）时，A 建现场时补齐，诊断中才发现缺的，发现时补；开 B 时写进 `handover.md` 的「依赖」。只是要调用的脚本，照 [files.md](files.md) 的「执行口径」写绝对路径，不拷。项目规定里只说构建或打包前要补的，跑测试前同样要补。
5. 查提交身份：在 worktree 里运行 `git var GIT_AUTHOR_IDENT` 和 `git var GIT_COMMITTER_IDENT`，看 git 实际会用的身份。环境变量 `GIT_AUTHOR_*`、`GIT_COMMITTER_*` 也算在里面，优先级还高于 `git config` 和 `-c`，所以只看 `git config` 会看错。两条打出同一个名字和邮箱（不是 `用户名@主机名` 这种系统猜的），就用它。报错、两条不同或像系统猜的，算缺身份：从 `git -C <主仓库> log -5 --format="%an <%ae>"` 里挑候选；主仓库是新克隆、log 里没有用户本人的提交时，从本机同组其他仓库的仓库级配置找；留到确认提问时问用户。用户定的身份和 `git var` 不同时，A 自己 commit 也按 [b.md](b.md)「边界」的提交身份写法。
6. flow 仓库不存在时：建目录，`git init`，按 [files.md](files.md) 建 `registry.md`，commit。flow 仓库没有可用的提交身份时，给它配仓库级身份：`user.name` 为 `fixing-bugs-duo`，`user.email` 为 `fixing-bugs-duo@localhost`。flow 仓库只在本机用，这个身份不会进任务分支。建本任务子目录 `<短名>/`；空目录 git 不记，等里面有文件再 commit。
7. 读 `registry.md`。「待收尾」里有别的任务的行时，在对话里列出短名和 MR/PR，不动它们。在「待收尾」追加本任务一行（已有就不加），MR/PR 写「未建」，估算步数和档位写「未定」（快修写「快修」），commit：从建好 worktree 起就有现场要收。快修只核对关键路径和历史翻车域两条，命中的不改档位，在交付报告里标出来，交付前的审查照第 4 步登记类豁免那一格做；然后去修。其余档位按「门槛硬条件」逐条核对，记下已命中、未命中和要问用户的，先不问，到第 4 步按需要再问。

**完成：** worktree、duo 目录和 flow 子目录都在，「待收尾」里有本任务，flow 仓库已 commit；对话里有目标分支、起点 sha、工作分支、提交身份，以及硬条件的现状（快修只有关键路径和历史翻车域两条）。

## 3. 诊断

在任务 worktree 里做 `fixing-bugs` 的 `full.md` 第 1–2 段。

- 原始复现命令和一次性 harness 放进 flow 的 `<短名>/repro/`，不放进 worktree。这样清理打点后它们还在，B 也能直接运行。复现数据来自线上记录（trace、日志、用户原话）时，先看项目对这类数据的存放规定：flow 仓库也是 git 仓库，规定不进 git 的数据放到项目指定的本机目录，`repro/` 里只放读取它的脚本和路径。
- A 自己搭复现、打点。同时派只读子 agent 并行侦察：代码路径、git 历史（`log -S`、`blame`、bisect 候选）、日志。用前台 Task，几个侦察 agent 和 A 自己的打点命令放在同一条消息里发出，一起返回，不用等通知。每个子 agent 只拿一句现象和它负责的那个问题，交回带证据（路径加行号，或 commit sha）的结论，交回方式同 [review.md](review.md)「全量审查的编排」第 1 条；不让它们运行复现命令，免得和 A 的打点抢 worktree，也不让它们写任何文件，临时目录也不写。日志或 trace 已经直接记下根因机制时（见 `full.md` 第 2 段），不派侦察，A 做那次全量核对。
- 干净的 worktree 复现不出、而主仓库能复现时，先看 `git -C <主仓库> log --oneline HEAD..<起点 sha>`、`git -C <主仓库> log --oneline <起点 sha>..HEAD` 和 `git -C <主仓库> status --short`。第一条有输出，可能是上游已经修好；后两条有输出，bug 可能依赖主仓库没推送的 commit 或未提交的改动。停下把看到的告诉用户：上游已修就结束任务；依赖本地改动时，问用户先把这些改动提交到一个分支、再从那个分支重建 worktree，还是只带哪几个文件。A 不擅自搬运改动。

**完成：** `full.md` 第 2 段的完成条件全部满足；复现命令和 harness 在 flow 的 `repro/` 里，并已 commit。

## 4. 分流

按根因估算执行顺序，不含 S0 准备步骤。再按诊断时实际跑过的耗时，估一轮「原始复现加相关测试」要多久，下表简称「一轮耗时」。风险信号按第 3 步拿到的证据判：第 3 步之前判过的信号被诊断推翻时（例如以为会影响存量数据，重跑后没有影响），在对话里写明推翻它的证据，按现在的事实分流。

| 情况 | 做法 |
|---|---|
| 没命中硬条件，并且满足其一：≤2 步；≤4 步且一轮耗时不超过 5 分钟 | **豁免**：A 不开 B，自己在任务 worktree 里按 `fixing-bugs` 修完。没有风险信号时接排查档第 3 步；有风险信号时接 `full.md` 第 3 段，文档放 flow 的 `<短名>/`。按「停下与交付」收尾，其中的「交付前审查」跳过，审查按本格下文做。收尾后，A 按路径 `git add` 本轮改动和新文件，用记下的提交身份 commit。3–4 步的豁免，接着按 [review.md](review.md) 的轻量版派 1 个审查 agent 看维度 1、2，审本任务的 commit（`<起点 sha>..HEAD`）；没有 flow 文档时，给它的文档片段换成根因、修好标准和回归测试的期望。审出的问题修好后，重跑原始复现和相关测试，再另 commit。然后按下文「交付前同步」处理目标分支的新 commit，`git -C <worktree> push -u <远端> <工作分支>`，向目标分支建 Draft MR/PR，描述写根因、改法和验证命令，按下文「交付报告」报告，写明为什么没开 B，再做第 9 步。 |
| 命中的硬条件只有关键路径或历史翻车域，≤2 步，改动只是往已有的登记表、枚举或清单里加减条目，读它的代码不改 | **登记类豁免**：照上一格的豁免做，本 skill 别处说豁免的地方都包括它，只是审查换成 [review.md](review.md) 全流程的编排：维度 1、2 各派一个审查 agent，审 `<起点 sha>..HEAD`。A 先用 grep 列出改动处的全部读取方（读这张表、调这个函数的代码，路径加行号），交给维度 1 的 agent，要它逐个说明行为变了没有。命中历史翻车域时，那几次翻车的判据各要有一条测试覆盖，已有的指出是哪条。 |
| 其余没命中硬条件、≤8 步的 | **轻量版**：只在最后一步标 `[M]`，只在最后一步的完成 commit 上做一次全量审查 |
| >8 步，或其余命中硬条件的 | **全流程**：`[M]` 按 [files.md](files.md) 的规则标，每个 `[M]` 做一次全量审查；历史翻车型判据各写一条锚定断言 |

开 B 有固定开销：写 7 个以上 flow 文件、起监视脚本、每步审查。步数少、测试又快时，A 自己修更快。B 划算的是测试慢、步骤多，或有活能并行的 bug。

轻量版和全流程都锚定第一条正式回归测试（锚定断言 A-1）。

有事要问用户时（硬条件拿不准、目标分支待用户、缺提交身份），按分流结果定时机：
- 豁免：现在一次问齐，等回答再分流或交付。
- 轻量版：先按轻量版往下做，问题并进第 6 步的确认提问；答案命中硬条件就改成全流程。
- >8 步：直接走全流程，问题并进第 6 步的确认提问。

用户事先授权 A 自选时，哪些仍要问见第 6 步。

**完成：** 对话里有估算步数、一轮耗时、硬条件结论、分流结果和理由；豁免时已转去单会话修复。

## 5. 先开 B 做准备

1. 按 `fixing-bugs`「停下与交付」第 1 步，清掉 worktree 里的打点，直到 `git status --short` 为空。
2. 按 [files.md](files.md) 写 `handover.md` 和 `steps.md`。`steps.md` 至少有 S0；交接材料已经写完时，可以直接写完整版，B 本轮照样只做 S0。再把 `rulings.md`、`batch.md`、`review-state.md` 建成只有标题的骨架（`last_reviewed_sha` 填 worktree 当前 HEAD），commit。B 启动时就要读这些文件。
3. 用后台子 agent 开 B（Cursor：`Task`，`run_in_background: true`，之后每次 resume B 也带上它，否则 A 会一直等到 B 这一轮结束。用户指定了 B 或审查 agent 的模型，或者用户规则规定了子 agent 怎么选模型时，按它填 `model`，并记进 `handover.md` 的「模型」），提示词：

```text
你是 fixing-bugs-duo 的执行会话 B。先读 <本 skill 目录>/b.md，按它执行。
- 任务 worktree：<路径>（工作分支 <工作分支>）
- duo 目录（progress.md 和日志放这里）：<路径>
- flow 目录（只读）：<父目录>/<repo>-flow/<短名>/
- fixing-bugs 目录：<路径>
- 本轮：只做 S0，方案还没冻结
```

4. 把 B 的完整 agent ID 写进 `handover.md`，并在对话里告诉用户（带链接）。
5. 在后台起监视脚本，工作目录设为 flow 仓库，用宿主的输出通知唤醒 A。Cursor 用 Shell 的 `notify_on_output`，匹配 `^DUO_(WAKE|ERROR)_<短名>`。步骤超时 `<N>` 用 `handover.md` 里的值。B 的转录用开 B 时宿主返回的路径：
   - Windows：`powershell -NoProfile -ExecutionPolicy Bypass -File <本 skill 目录>/scripts/watch.ps1 -Worktree <路径> -Tag <短名> -Transcript <B 的转录> -StepMinutes <N>`
   - 其他：`DUO_STEP_MINUTES=<N> bash <本 skill 目录>/scripts/watch.sh <路径> <短名> <B 的转录>`

   脚本靠转录末行的 `"type":"turn_ended"` 判断 B 一轮结束了，这是 Cursor 转录的格式。宿主开子 agent 时不返回这种转录路径的（不是 Cursor），不猜路径：Windows 去掉 `-Transcript`，其他平台去掉 `<B 的转录>`。这时 READY 行的 `transcript=False` 是正常的；脚本不发 `stall` 和 `slow`，改发 `heartbeat`，由 A 按 supervise.md 核对。B 仍是 A 的子 agent，resume 和 interrupt 照常走宿主的通道。

   脚本先打一行 `DUO_READY_<短名> pid=<pid> …`，之后每行是 `DUO_WAKE_<短名> <序号> <事件>`。事件的含义和处理见 supervise.md。

   起脚本后，先等到 `DUO_READY` 行再往下做（Cursor：AwaitShell 匹配 `^DUO_(READY|ERROR)_<短名>`）。等到的是 `DUO_ERROR_` 行时，按它写的原因修好再起。传了转录、READY 行却是 `transcript=False`，说明路径错了，同样修好再起。把 `DUO_READY` 行里的 pid 写进 `handover.md`。

   **停和重启脚本**：一律按 `handover.md` 里的 pid，也就是脚本在 READY 行自报的 pid。宿主报的 PID 可能是外层 shell，停掉它，脚本还会在；宿主报告 shell 退出时，脚本也可能还在。
   - 停：`Stop-Process -Id <pid>` 或 `kill <pid>`。
   - 重启：脚本打了 `DUO_ERROR_` 行、宿主报告它的 shell 退出、换 B、转达 MR/PR 评审意见、A 压缩后发现它不在（`handover.md` 写了「已停」的除外）时，都要重启。
     1. 除了打过 `DUO_ERROR_` 行（脚本已经自己退出），先查这个 pid 是不是还是这个脚本：Windows 用 `(Get-CimInstance Win32_Process -Filter "ProcessId=<pid>").CommandLine`，其他平台用 `ps -p <pid> -o args=`，输出里有 `watch` 和 `<短名>` 才算。是就先停掉，免得两个脚本同时发唤醒；不是或查不到，说明它已退出，pid 可能被别的进程占了，不要停。
     2. 用和上次同一种起法再起：上面第 5 条的命令，或退路第 2 条的命令。等到 READY 行，更新 `handover.md` 里的 pid 和转录。
     3. 脚本停着期间，B 的 commit 和 R-n 不会唤醒 A，所以先拍一次快照补审。

   worktree 删掉后，脚本打一行 `DUO_EXIT_<短名>` 自己退出，这一行不唤醒 A。

**退路：两个独立聊天。** 宿主没有后台子 agent，或不能给运行中的子 agent 发消息时：
1. A 把上面的提示词写进 flow 的 `<短名>/b-prompt.md`，请用户新开一个聊天粘贴。
2. 监视脚本打开 `status` 事件，不传转录：Windows 在上面第 5 条的命令里去掉 `-Transcript`，加 `-WatchStatus`；其他平台去掉 `<B 的转录>`，在命令前加 `DUO_WATCH_STATUS=1`。B 每次停下都写 `progress.md` 的 `STATUS:` 行，A 靠 `status` 事件知道。
3. A 给 B 的指令（开始 S1、BLOCKING 答复、P0、DoD 撤销）追加进 `handover.md` 的「给 B 的指令」，编号 `I-<n>`。commit 后，请用户在 B 的聊天里发「继续」。B 在跑时不用转达，B 会在定点读时读到。
4. B 的 BLOCKING 请求等 30 分钟没有答复时，B 直接问用户。

**完成：** worktree 干净，B 在跑 S0，用户已拿到 B 的 ID，监视脚本在跑，`handover.md` 已 commit。

## 6. 写交接材料并冻结

B 跑 S0 期间，A 在 flow 的 `<短名>/` 里写交接材料。这期间 A 要亲手跑代码的（生成器、原型、修复前读数），在起点 sha 的临时 detached worktree 里跑，任务 worktree 归 B。
1. `problem-and-solutions.md` 和 `test-plan.md`：按 `full.md` 第 3–4 段写，路径换成 flow 子目录。B 跑不了的用例（要用 B 拿不到的外网、真实模型、生产数据等），在用例行写「执行者：A 验收」。这类用例要用来证明修好的，A 现在就在没修的环境上先跑一次，读数写进用例行的「修复前读数」；复现不出症状的，改标为回归检查，并写明修好由哪条用例证明。重放类用例的 harness 按 `full.md` 第 2 段核对每个输入的来源。上线后才跑的用例，按第 1 步「有上线后才做的核对时」那段写。
2. `steps.md`：执行顺序，每步附完成判据和对应的用例编号，标 `[M]`，末尾写 DoD。诊断时已定位到的代码段贴进对应步骤，B 从它下手，不用整读大文件。方案要重新生成某个生成文件时，A 先在起点 sha 上跑一次生成器：有 diff，说明它在目标分支上本来就过期，在这一步里写定怎么处理（例如只提交本任务相关的那份），不留给 B 碰上再停。
3. `rulings.md`：预埋区（勿翻案项，以及预见到的歧义和预设答案），锚定登记。方案要解析真实数据时，A 冻结前在真实数据上跑一次原型，发现的坑写成预设答案。方案放宽或收紧某项判定时，预设答案写明既有测试因此变红怎么办，例如停下写 BLOCKING、不自己改断言。
4. `anchored/A-1.*`：第一条正式回归测试的断言文本。

格式见 [files.md](files.md)。

然后用一次提问请用户确认：推荐方案、测试 seam、分流结果（轻量版或全流程），以及第 4 步并进来的问题。用户已授权 A 在范围内自选时（例如「不用我参与」），记下授权原话和时间，不再问，同时调用的其他 skill 要求追问用户的也一样；授权不覆盖这几样，仍要问：supervise.md「要用户拍板的事」、需要外部裁决的改动、放宽验收门槛、超出用户给的范围。等待期间可以继续完善文档。

确认后，答复写进对应文件，commit flow 仓库。冻结要等两件事都到位：用户确认，以及 B 回了 `S0-DONE`、按 supervise.md 的 `S0-DONE` 行核对通过。后到的那件一到就冻结：打 tag `<短名>-v1`，在 `handover.md` 写方案版本，commit，再 resume B：「方案 v1 已冻结，读 steps.md，从 S1 开始」。B 还在跑 S0 时，不 resume，也不 interrupt；用户在步骤超时时选了「打断 B」除外。B 在 S0 里回了 `PAUSED`（例如缺不入仓文件）的，按 supervise.md 的 `PAUSED` 行处理完就 resume 它，S0 做完才冻结。

**完成：** 文件齐全；用户确认或授权有记录；tag 已打；B 已收到开始指令。

## 9. 收尾

MR/PR 合入、用户放弃，或任务在交付前就结束（例如上游已修、评测门槛没过）之后做，快修和豁免同样做；交付前结束的按下面的「放弃」清理。接手的会话从 `registry.md`「待收尾」里本任务那一行拿 worktree、工作分支、远端和门槛判例的估算：
1. 在 `registry.md` 回写：
   - 本任务发现的 P0/P1 和所在模块
   - 新的历史翻车域
   - 跨任务有效的勿翻案项
   - 硬条件里用户的答复，以及「用户不确定」的模块
   - 门槛判例：估算步数、实际步数、档位
2. 任务目录里还要补的记录（例如 `review-state.md` 的合入记录、`test-plan.md` 的上线后读数）先写完并 commit，再归档：`git mv` 只搬索引里的版本，没 commit 的改动会留在工作区。`git -C <flow 仓库> ls-files <短名>` 有输出时，建 `archive/` 目录（已有就跳过），执行 `git mv <短名> archive/<短名>`；`archive/` 不存在时 `git mv` 会失败。没有输出（快修常这样）时，`<短名>/` 是 git 没记的空目录，`git mv` 会报错，直接删掉它。然后 commit `registry.md` 和归档，再运行 `git -C <flow 仓库> status --short -- registry.md archive/<短名>`，应为空。
3. 监视脚本还在跑，就按 `handover.md` 里的 pid 停掉。
4. 清理现场。删 worktree 前：
   - 运行 `git -C <worktree> status --short`。只剩运行生成物时，下面的 `worktree remove` 加 `--force`，否则 git 会因为未跟踪文件拒绝删除。还有别的改动或未跟踪文件时，先弄清是谁写的、要不要留，不加 `--force`。
   - A 的 shell 先切出 worktree，从那里启动的后台进程也要停掉。Windows 上，只要还有进程的工作目录在 worktree 里，删除就会失败。这时 git 已注销这个 worktree，只剩目录，切出、停掉这些进程后再删目录。
   - 已合入：`git -C <主仓库> worktree remove <worktree>`，duo 目录随之删掉；再 `git -C <主仓库> branch -d <工作分支>`。它报 `not fully merged` 时（推送时没带 `-u`、squash 合入、平台合入前变基过分支，都可能这样），确认 `git -C <主仓库> rev-parse <工作分支>` 等于 MR/PR 的最后一个 commit，或等于平台变基前的 head（在 MR/PR 的版本历史里），再改用 `branch -D`；都不相等就停下问用户。再看远端分支：`git -C <主仓库> ls-remote --exit-code <远端> refs/heads/<工作分支>`，退出码 2 是已删，0 是还在，其他是查不了，停下说明。还在、MR/PR 设了合入后删除源分支、它的 sha 又等于 MR/PR 的最后一个 commit 时，运行 `git -C <主仓库> push <远端> --delete <工作分支>`（合入机器人常常不删）；sha 不相等就停下问用户；MR/PR 没设删除源分支的，留着。
   - 放弃：同样删掉 worktree，本地分支用 `branch -D` 删。远端分支删不删、Draft MR/PR 关不关，在同一条消息里问用户，默认保留。
5. 现场清完，删掉 `registry.md`「待收尾」里本任务那一行，commit。用户要求保留现场，或删 worktree 没成功时，这一行留着，在「备注」写明原因。

**完成：** `registry.md` 和归档已 commit；监视脚本已停；worktree 和本地分支已删，「待收尾」里没有本任务；或者现场保留、原因写在「待收尾」那一行。

## 交付前同步

第一次 push 工作分支之前做：快修和豁免在 push 前，开了 B 的任务在 supervise.md 第 8 步的独立验收之前。
1. 起点是 `HEAD`（第 2 步第 2 条）时，做完第 2 条就结束。否则 `git -C <worktree> fetch <远端> <目标分支>`；fetch 失败也是做完第 2 条就结束，在对话里说明。
2. 第 1 步第 2 条列出的、改到同几个文件的别的任务，还没合入的，交付报告里写明和它们的先后。
3. `<远端>/<目标分支>` 还是起点 sha，或者项目规定不变基时，到此为止；后一种在交付报告里写明目标分支动过。
4. 变基，开了 B 的任务要 B 停着（怎么判断见「现场」）、终审 agent 已交回：先记下 HEAD 的 sha。第 2 步第 5 条记下的提交身份和 `git var` 打出的不同时，照 [b.md](b.md)「边界」设好四个环境变量（变基会重写提交者）。再 `git -C <worktree> rebase <远端>/<目标分支>`，有冲突就 `git -C <worktree> rebase --abort`，停下问用户。
   - 核对：`git -C <worktree> diff --numstat <起点 sha>...<变基前的 HEAD>` 和 `git -C <worktree> diff --numstat <远端>/<目标分支>...HEAD` 应逐文件一致，不一致就看清差在哪，说不清就停下问用户。行数一致也可能放错了位置：`.gitattributes` 里按 `merge=union` 合并的文件（例如 CHANGELOG）逐个看 diff，错位的改好另 commit，身份同上，开了 B 的任务带 `Flow: docs`。
   - 起点 sha 改记成新的 `<远端>/<目标分支>`。开了 B 的任务同时改 `handover.md` 的起点，把 `review-state.md` 的 `last_reviewed_sha` 改成新 HEAD、注明「变基自 <旧 sha>」，commit flow 仓库；之后再 resume B 时，消息里写明分支已变基到哪个 sha。
5. 在新 HEAD 上重跑验证：快修和豁免重跑原始复现和相关测试；开了 B 的任务接着做独立验收，它本来就在最终 sha 上跑。

## 交付报告

Draft MR/PR 建好或确认建不了之后，报告之前：
1. 刚建好的 MR/PR 读回一次：建的时候平台自动挂上的 Assignee 和 Reviewers 清掉；项目规定要保留的，在报告里写明是谁、为什么在。之后的轮次（例如转达评审意见后再报告）不再清，那时的审查者是人加的。
2. 在 `registry.md`「待收尾」本任务那一行填上 MR/PR、估算步数和档位（这一行第 2 步就该有，没有就补上），commit flow 仓库。合入可能隔几天、换个会话才定，第 9 步和接手的会话靠这一行找到现场。

然后 A 向用户报告：
- 最终档位，以及是否豁免、豁免理由；快修命中的硬条件
- 根因
- 改动
- 验证证据
- MR/PR 链接和目标分支
- 两份文档的路径
- 跨仓库任务：仓库之间的合入和上线顺序
- 仓库外的记录活：做了什么、链接
- 契约或给别的团队的文档里，核对不了出处的事实
- 一次请求有好几个问题时：分拣表的路径
- 用户事先授权 A 自选时：A 替用户定了哪些事
- 待用户拍板的事项，固定包含每张 MR/PR 合不合入（用户已授权合入的除外）
- B 在 `progress.md`「流程摩擦」里记的条目，原样附在末尾；没有就不写

合入默认由人确认：A 和 B 都不合入，也不做等同于批准合入的动作，例如标记 ready、指派会自动合入的审查者。用户明确授权合入时（例如「MR 能合就合」），A 记下授权原话（开了 B 时写进 `handover.md` 的「合入授权」），按项目的合入流程跟到合入，做法见 supervise.md 第 8 步。B 始终不合入。

**快修和豁免的 MR/PR 评审意见**：定级和回应同 supervise.md 第 8 步「MR/PR 评审意见」，只是没有 `batch.md`，留给后续 MR/PR 的直接告诉评审人。要改代码的由 A 自己改：
1. 先核对：评审要的改法碰到 `fixing-bugs` 的升档信号，或者让豁免够不上第 4 步它那一格的条件时，停下问用户。
2. 在 `registry.md`「待收尾」本任务那一行的 worktree 里改。先 `git -C <worktree> fetch <远端>`；远端分支有本地没有的 commit（例如评审人在网页上应用了建议）时，`git -C <worktree> merge --ff-only <远端>/<工作分支>`。平台变基过分支时它会报 `Not possible to fast-forward`：`git -C <worktree> status --short` 为空、本地 HEAD 又等于 MR/PR 变基前的 head（在 MR/PR 的版本历史里）时，改用 `git -C <worktree> reset --keep <远端>/<工作分支>`；不满足，或别的原因合不了，停下问用户。
3. 提交身份沿用交付时的作者：`git -C <worktree> log --reverse --format='%an <%ae>' <远端>/<目标分支>..HEAD` 的第一行，目标分支看 MR/PR（平台变基后提交者可能换成了机器人，所以只看作者）。它和第 2 步第 5 条两条 `git var` 打出的不一致时，按 [b.md](b.md)「边界」的提交身份写法 commit。
4. 重跑原始复现和相关测试。原始复现在 flow 的 `<短名>/repro/`，没有时用 MR/PR 描述里的验证命令，再没有就问用户；flow 里有 `test-plan.md` 时，相关测试换成其中全部本轮必做用例，结果写回并 commit flow 仓库。
5. 另 commit，`git -C <worktree> push`（MR/PR 已在，不再建），按本节报告。
