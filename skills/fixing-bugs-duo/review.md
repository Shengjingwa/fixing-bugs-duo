# A 的审查

## 怎么读 B 的东西

- 读 git 一律用 `git --no-optional-locks -C <worktree> <log|status|diff|show>`。选项放在子命令前面。`status` 和 `diff` 会刷新 index、抢 `index.lock`，不加这个选项，B 会偶发 commit 失败。
- 审查钉在 sha 上：用 `git show <sha>` 和 `git diff <sha1>..<sha2>`，不读 B 正在改的工作区。
- B 的用例状态和红绿证据在 duo 目录 `progress.md` 的「用例记录」里，日志在 `logs/`。
- 要亲手运行代码时：B 停着就在任务 worktree 里跑；B 在跑就开临时 detached worktree。规则见 SKILL.md「现场」。

## 严重度

审查 agent 只给候选等级，最终等级由 A 亲验后定。

| 等级 | 条件 | 处理 |
|---|---|---|
| **P0** | 已确认，且满足任一条：原始复现在声称修好的 sha 上仍失败；回归测试的期望被反转或掏空（假绿）；锚定断言的核心行被改，且没有已批准的 R-n；修法只遮住症状，而方案要求消除或隔离根因；关键路径行为错误或回退；数据丢失或不可逆副作用 | 阻断 DoD，立即 interrupt B |
| **P1** | 已确认违反方案或测试计划条目，但不在关键路径上、没有数据丢失；或高度疑似 P0、还没亲验；或生产路径残留诊断前缀 | 写进 `batch.md`。B 在下一个 `[M]` 前修好；最后一个 `[M]` 发现的，在 DoD 前修好。也可以经用户批准遗留 |
| **P2** | 可维护性、测试覆盖建议、文档与风格；缺 `Flow:` trailer（流程类） | 攒批写进 `batch.md`，最后进 MR/PR 描述，不阻断 |

## 触发分级

| commit | 做法 |
|---|---|
| `Flow: step`，说明里带「收尾清理」 | B 收尾时清打点和锚定标记的 commit，先于下面各行匹配，只轻检：`git show` 里只有删掉的 `[DEBUG-duo]` 行、本任务的 `ANCHORED` 首尾行和行末的 `CORE` 注释，核心行其余部分逐字没变。还有别的改动时，那部分按「不是 `[M]`」那一行轻检 |
| `Flow: step`，该步是 `[M]` | 全量审查本周期的 commit 区间（上一个 `[M]` 之后到这个 commit）。最后一个 `[M]` 审整个任务区间，兼作终审。最后一个 `[M]` 是没有 commit 的验证步时，A 收到 `STATUS: DOD` 后审到「收尾清理」之前的那个 commit，没有清理 commit 就审到 `HEAD`；审完 `last_reviewed_sha` 留在 `HEAD`，不回退 |
| `Flow: step`，不是 `[M]` | A 亲自轻检：读 diff，扫 P0 形态，核对该步完成判据。这一步碰了关键路径时，还要核对第 8 维用例都绿。有用例标了还没到的转绿步时，核对它红的原因没变。B 的 `progress.md`「用例记录」可能比 commit 晚一两分钟写好，没写时先审 diff，用例记录留到下次醒来再核 |
| `Flow: wip` | 不审，快照时看有没有明显异常 |
| 带 `Flow: anchored-adapt` | 先按同一 commit 的另一个 trailer 处理；只有它一个时按「没有 trailer」处理（脚本不会为它唤醒 A，下次醒来时补审）。不论哪种，下次醒来时都逐块比对 `CORE` 行和 `anchored/` 原文 |
| `Flow: fix` | A 必须亲验复核，不能只看 B 的回执。修复碰到锚定断言覆盖的逻辑或关键路径时，补一轮增量审查 |
| `Flow: docs` | 跳过，在 `batch.md` 记一条跳过记录 |
| 没有 trailer | 按 `step` 从严处理，并记一条 P2 |

快照发现异常或用户要求时，A 可以把任何 commit 升级为全量审查。轻量版只有最后一步是 `[M]`，所以全量审查只在最后一步的完成 commit 上做，审整个任务区间。

## 全量审查的编排

1. 派只读审查 agent，互不知道对方：
   - 全流程：维度 1、维度 2 各一个 agent。本任务碰了 `registry.md` 的关键路径时，把关键路径清单交给维度 1 的 agent，让它同时看「关键路径行为不变」。
   - 轻量版：只派一个 agent，看维度 1 和 2。
   - 维度 3、4 都是命令能查完的事，由 A 自查，不派 agent。

   用前台 Task，两个审查 agent 和 A 自查的命令放在同一条消息里发出，一起返回。每个 agent 只拿：commit 区间和 `git diff` 命令、它负责的维度的检查项、需要的文档片段（见下表），再加这段固定前缀：「只读。git 一律写成 `git --no-optional-locks -C <worktree> …`，选项在子命令前；读文件用 `git show <sha>:<路径>`，不读工作区；不跑测试；不写任何文件，临时目录也不写，要比对就用 `git show <sha>:<路径>` 接管道，或 `git diff <sha1> <sha2> -- <路径>`。」每个 agent 交回候选清单，每条写编号、sha、路径加行号、证据、候选等级。完整清单写在它的最后一条消息里：Cursor 只把子 agent 的最后一条消息交回 A。宿主不把子 agent 的结果自动交回时（例如 Claude Code 里转入后台的 agent，做完只是变成 idle），提示词末尾写明用宿主的消息工具把最终清单发给 A。agent 结束了却没交回清单，A 给它发一次消息要。
2. A 亲验每一条 P0 候选。P0 确认后，马上落盘并 interrupt B，不等核实。
3. P1 候选多于 2 条时，交给一个对抗核实 agent，它的默认立场是「误报」，只拿候选和证据，带同样的固定前缀，和 A 亲验 P0 同时开始。A 用一条命令就能确认或驳回的候选（例如诊断前缀、缺 trailer）由 A 直接定，不交给它。
4. 核实结论和 A 的亲验冲突时，以 A 的亲验为准。A 是裁决者，核实 agent 只是过滤器。
5. 被驳回的候选连同驳回理由写进 `batch.md`，不静默丢弃。终审时 A 逐条复读驳回项。
6. 落盘并 commit flow 仓库之后：P0 立即 interrupt B；P1 和 P2 留在 `batch.md`，等 B 定点读。
7. B 修完（`Flow: fix`）后 A 亲验。同一问题 3 轮没修好，升级用户。

宿主限流时，先派维度 1，维度 2 的抽样顺延到下一个 `[M]`。

## 维度

| 维度 | 检查什么 | 给 agent 的文档片段 |
|---|---|---|
| 1. 方案符合性 | 只实施了选定方案；没碰禁区；根因被消除或隔离，不是遮住症状。修法只能靠评测读数判对错时，另查 SKILL.md 第 1 步「修法的对错只能靠评测读数判时」那段的第 4 条：数据集没覆盖的输入 | `problem-and-solutions.md` 的选定方案、根因、禁区；评测类修法另给门槛文件（flow 的 `<短名>/`）和数据集路径 |
| 2. 断言方向抽样 | 抽 K 条断言，K = min(10, 本周期新增和修改的断言数)，必抽下面两类，其余随机补足。核对每条断言测的是方案和测试计划的要求，而不是代码现状。另外逐行过本周期用例在 `test-plan.md` 里的「可观察结果」，不受 K 限制：每个子要求指出钉住它的断言，以及哪种写错的实现会让它变红；指不出来的记 P1 候选 | `test-plan.md` 的对应用例行；`anchored/` 原文；`rulings.md` 的锚定登记 |
| 3. 相邻功能（A 自查） | `test-plan.md` 第 8 维的用例都在，`progress.md`「用例记录」里都是 green；必要时在 B 停着时亲手跑一遍 | `test-plan.md` 第 8 维 |
| 4. 清洁与攒批（A 自查） | 生产路径没有诊断前缀（`git grep` 搜）；`git diff --stat` 里没有与 bug 无关的文件；`git diff --check <起点 sha>..HEAD` 无输出（起点 sha 见 `handover.md` 的「工作分支」行；仓库文件以 CRLF 存储时加 `-c core.whitespace=cr-at-eol`；有输出记 P2）；`git log --format=%B` 里 trailer 齐全；`batch.md` 里该本周期修的条目已修 | `batch.md`；诊断前缀 |

维度 2 必抽的两类：
- 同一个 commit 里，既改了被测实现，又改了对应断言的期望值。这是假绿的典型形态。
- 本任务加的全部 ANCHORED 块：逐块和 `anchored/` 原文比对，带 `CORE` 的行必须逐字一致。不一致且没有已批准的 R-n，记为 P0 候选。目标分支上原有的块是以前的任务留下的，不比对。B 收尾删掉标记之后的 commit（例如修评审意见），拿 `anchored/` 里的核心行到测试文件里逐行找。

## 每轮之后

轻检和全量审查之后都做：
1. 更新 `review-state.md`：`last_reviewed_sha`、当前周期、在途审查项。
2. 发现写进 `batch.md`，P0 同时写清 interrupt 时发给 B 的消息。
3. commit flow 仓库，然后才通知 B 或回复用户。

红绿证据在 `progress.md`「用例记录」里，duo 目录到第 9 步删 worktree 时才消失，所以每轮不用转抄，审查直接读那张表。转抄在 supervise.md 第 8 步验收时一次做完。
